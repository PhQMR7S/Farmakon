تاريخ المراجعة: 27 أكتوبر 2026. النطاق: فرع `audit/f00-regression-2026-10-26`، [Draft PR #18](https://github.com/PhQMR7S/Farmakon/pull/18) إلى `feat/farmakon-v2-p0-privacy`، مع بقاء الاعتماد على #17 وIssue #1 مفتوحة. لا دمج أو نشر Production أو تعديل نتائج حقيقية.

## 1. نقطة البداية والحالة بعد التعديل

تحقق HEAD الفعلي عند البداية بـGitHub و`git ls-remote`: `557842ac39a340a0d60406f66e103494298f0c74`. راجعت التقرير السابق ونتائج [CI 40464117157](https://github.com/PhQMR7S/Farmakon/actions/runs/40464117157): baseline/postgres/browser ناجحة؛ 30 Browser E2E سابقاً. لم أعد دورة حذف F00.5 الحية.

الموجود سابقاً: Snapshot يتضمن الأسئلة ومفاتيحها عند البدء، `deadline` محفوظ، معاملات SERIALIZABLE مع إعادة محاولات آمنة عند 40001/40P01، وصلاحيات حية عبر `canReadAttempt`. هذه ضوابط سابقة محفوظة، وليست إصلاحات جديدة يُنسب إنجازها لهذه الجولة.

بعد F00.6: للمحاولات الجديدة بداية وموعد موحدان و`timingVersion:2`، تجميد خادمي للإجابات عند الموعد، حفظ على شكل patches، وتسوية حتمية عند طلب مصرح لاحق. الواجهة تستأنف الموعد نفسه، تعرض تأكيد الحفظ وفشله والانقطاع، وتعرض النتائج المسوّاة عند العودة. لا Cron أو عامل دوري جديد.

## 2. الأخطاء المؤكدة وخطورتها

| النتيجة | الخطورة ضمن سياق الامتحانات | المعالجة |
|---|---|---|
| `submitExam` يقبل إجابات جديدة حتى 15 ثانية بعد deadline بينما save يوقفها | High: تجاوز حد وقت الإجابة عبر مسار آخر | v2 لا يقبل مدخلات جديدة عند/بعد الموعد؛ يصحح المحفوظ فقط |
| GET يخفي المحاولات المنتهية؛ إعادة البدء تتجاوز محاولة نشطة منتهية بلا تسوية | Medium: فقدان حالة النتيجة عند غلق الصفحة | تسوية كسلية ذرية، وإتاحة آخر نتيجة مسموحة |
| ساعة الهاتف تضبط العداد والتسليم التلقائي | Medium: عرض مضلل وتأخر طلب العميل؛ الخادم كان يملك deadline أساساً | مرساة serverNow مع performance.now وإعادة مزامنة عند الاتصال/الظهور |
| الحفظ يستبدل خريطة الإجابات كاملة؛ جهاز قديم يمكنه إسقاط مفاتيح حفظها جهاز آخر | Medium: ضياع إجابات مؤكدة | merge خادمي، وواجهة ترسل السؤال المتغير فقط وتسلسل طلباتها |
| وقت deadline المُرسل يُحسب مرة أخرى بعد حفظ المحاولة | Low: اختلاف صغير بين الخادم والواجهة | حساب startedAt/deadline مرة واحدة لكل محاولة ناجحة |

لم يثبت خلل جديد في عزل Staging أو Strict Sessions أو RLS. هذا حكم على النطاق المفحوص، وليس شهادة خلو عامة من الثغرات.

## 3. السياسة الدقيقة للوقت والتصحيح

### المحاولات الجديدة v2

- `startedAt` و`deadline = startedAt + minutes*60000` من ساعة الخادم، محفوظان مع Snapshot JSON نفسه. لا يؤخذ وقت أو مدة أو هوية من العميل.
- الحد المعتمد نصف مفتوح: يقبل حفظ/إجابات التسليم حين `server processing time < deadline`. عند المساواة أو بعدها يُغلق إدخال الإجابات. الطلب المرسل قبل الموعد ووصل إلى المعالجة بعده لا يُعتمد كإجابة في الوقت.
- `saveExam` هو اسم API الحالي للعملية التي وصفها الطلب بـsaveAnswer؛ لا تغيير غير لازم للعقد. يقبل patch للأسئلة الموجودة في Snapshot فقط؛ السؤال الغريب 400. غياب مفتاح من patch لا يحذف إجابة مؤكدة.
- التسليم قبل الموعد يقبل مدخلات العقد القديم بعد التحقق منها ودمجها. واجهتنا تنتظر طلبات الحفظ المعلقة ثم تسلم `{answers:{}}`، ليكون المعتمد ما أكده الخادم. لا ترفع الواجهة اختياراً فشل حفظه عبر مسار التسليم كنجاح صامت.
- عند/بعد الموعد: submit يتجاهل الإجابات المرفقة ويصحح المحفوظ. save يرد 409 وقد يسوّي المحاولة داخل المعاملة؛ GET/start المصرح يسوّي المنتهي. `expired` يدل على تجاوز موعد الإجابة، و`late` يحتفظ بتعريفه التاريخي: أكبر من deadline+15000.
- هامش 15 ثانية باقٍ كتصنيف تأخر/مهلة وصول تسليم، وليس وقت إجابة إضافياً لـv2. يجوز طلب النتيجة لاحقاً؛ لا تُرفض النتيجة لمجرد التأخر، وتُحفظ إجابات الخادم.
- النتيجة وتغيير الحالة وسجل activity في معاملة واحدة. النتيجة done ثابتة؛ إعادة التسليم لا تعيد التصحيح، و`ON CONFLICT(user_id,kind,target) DO NOTHING` يمنع سجل نشاط مكرر.

### المحاولات القديمة

لم توثق المستندات المعتمدة سبباً معتمداً لهامش 15 ثانية؛ تفسيره كمهلة نقل استنتاج من الكود، لا سياسة مالك مثبتة. السلوك القديم كان يسمح باستبدال إجابات التسليم حتى `deadline+15000` شاملاً الحد، ثم يستخدم المحفوظ. لذلك أبقيت هذا التوقيت للمحاولات التي لا تحمل v2، ولم أعد تصحيح أي نتيجة done قديمة. لا تغيير جماعي للصفوف أو الدرجات.

يسوّي GET المحاولة القديمة بعد تجاوز نهاية هامشها، ويتركها قابلة للاستئناف أثناء الهامش مع إيقاف الاختيار في الواجهة عند deadline. سياسة v2 البديلة منفذة ومختبرة في فرع التطوير وStaging؛ اعتمادها للإنتاج يحتاج مراجعة المالك. لا نشر إنتاج في هذه الجولة.

بدء محاولة جديدة بعد اكتمال السابقة يبقى مسموحاً وفق السلوك السابق، بمعرف ومدة جديدين؛ لا تمدد للمحاولة نفسها. الواجهة تسميه «ابدأ محاولة جديدة». تحديد عدد الإعادات أو حظر مراجعة نتائج محاولات سابقة سياسة مستقلة لم تُخترع هنا. مفاتيح Snapshot النشط تُحجب؛ مراجعة نتائج محاولات تم تسليمها سابقاً تظل حقاً قائماً، ولا يمكن إلغاء معرفة سبق عرضها للطالب.

## 4. غلق الصفحة، ضعف الشبكة والاستئناف

انتهاء حق الإجابة لا يعتمد على وجود المتصفح. إغلاق كل أجهزة الطالب لا يشغل تسليماً فورياً في الخلفية: تبقى الحالة المخزنة active حتى طلب خادمي مصرح يسوّيها، لكن deadline قد انتهى ولا تُقبل إجابات جديدة. لا ادعاء بوجود Scheduler.

العداد يُعرض دقائق:ثوانٍ من مرساة serverNow ومؤقت monotonic؛ تغيير Date.now في الجهاز لا يضيف وقتاً. يعاد الاستعلام عند عودة الاتصال أو ظهور الصفحة بعد تعليقها. يتأثر عرض الوقت بزمن النقل/تعليق الجهاز؛ الحكم النهائي للخادم دائماً.

الحالات: جارٍ الحفظ / محفوظ / تعذر الحفظ. الإخفاق لا يظهر كنجاح؛ عند فقدان رد الشبكة قد يكون الطلب قد حُفظ فعلاً، ويُحسم ذلك بالاستئناف من الخادم. فشل سؤال سابق لا يغطيه نجاح سؤال مختلف. عند الانقطاع تُعطل الاختيارات، ويستمر الموعد. يظهر تحذير قرب النهاية، وبعدها توضيح أن النتيجة تعتمد على الإجابات المؤكدة وأن جلبها ينتظر الاتصال. لا تُخزن إجابات الامتحان أو مفاتيحه في PWA/Cache جديد.

## 6. الملفات والتوافق والتراجع

- `app/lib/server.ts`: helpers لحدود الوقت، patches، العرض الآمن والتصحيح الذري.
- `app/api/platform/route.ts`: تسوية GET داخل transaction، استرجاع نتائج مسموحة، start/save/submit، سرية الشرح.
- `app/platform.tsx`: العداد والمزامنة ورسائل الحفظ والانقطاع والاستئناف والنتيجة.
- `tests/backend-smoke.mjs`: Unit/handlers نفسها على SQLite وPostgreSQL، ساعة مضبوطة في عملية الاختبار فقط.
- `tests/privacy-smoke.mjs` و`tests/privacy-postgres.mjs`: منع عمليات الامتحان وكتابة نتيجته بعد قبول الحذف، بما فيها معاملة بدأت قبله.
- `tests/e2e/exam-integrity.spec.ts`: واجهة حقيقية مع HTTP transport اصطناعي، Desktop وPixel 7 وRTL ولوحة مفاتيح.
- `tests/live/exam-edge.ts` و`exam-preview.mjs` وREADME: أداة Staging مؤقتة مغلقة افتراضياً واختبار حي يدوي، لا CI حي تلقائي.
- `.github/workflows/quality.yml`: فحص syntax للاختبار الحي فقط؛ لا أسرار إضافية ولا تشغيل Staging في CI.

لا migration أو تعديل schema/RLS/grants أو TTL أو ساعة نظام. الإضافة تدريجية داخل JSON للصفوف الجديدة فقط.

التراجع الآمن: تثبيت الوصول إلى Preview السابقة أو استرجاع تغييرات الواجهة مع إبقاء قارئ v2 وحاجز deadline والتصحيح Idempotent؛ لا تُشغّل نسخة pre-v2 وحدها على محاولات v2 نشطة لأنها تعيد فتح هامش الإجابات القديم. انتظر تسوية المحاولات الجديدة أو احتفظ بالمعالج المتوافق. لا تمسح answers أو result أو ledger، ولا تعيد تصحيح المحاولات القديمة. إلغاء أدوات الاختبار مستقل عن التطبيق.

## 9. عزل البيئات والتنظيف

راجعت branch-specific overrides: Supabase URL مثبت على `qfzharpouemueipsrduv`، Strict Sessions وRate Limiting true، وميزة synthetic deletion false. قاعدة الاتصال بقيت في سجلها الحساس السابق ولم أستخرج أو أطبع كلمة مرورها. `assertPreviewIsolation` القائم يتحقق من تطابق قاعدة البيانات/Auth قبل أي اتصال؛ نجاح طلبات التطبيق على سجلات Staging الاصطناعية يثبت المسار الفعلي.
