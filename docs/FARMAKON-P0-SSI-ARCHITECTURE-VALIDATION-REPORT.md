## القرار الهندسي

**PARTIAL / EXPERIMENT — لا اعتماد للتصميم أو تطبيق حي.** تقسيم hash خفّض تعارضات المكونات في العينة، لكن التكرارات القديمة تمنع القيد المقترح، ويصبح نموذج النسخ قديمًا إذا سُمح بالكتابة بعد رفع القفل. نموذج المسارات التجريبي يغطي B1 فقط، وهو ليس محولًا جاهزًا للترحيل، ولم تُثبت الصلاحيات أو الحذف والاستعادة لمزود Supabase الحقيقي أو B2/B3/B4. تبقى بوابة SSI **FAILED / OPEN**؛ آخر اختبار حمل للتطبيق توقف عند 10 VU بسبب HTTP 503 / SQLSTATE 40001. لم تختبر 25 VU.

## نموذج مسارات التطبيق

[tests/ssi-runtime-p02.mjs](../tests/ssi-runtime-p02.mjs) يشغل handlers وhelpers الفعلية بعد ترجمتها فوق PostgreSQL ومحـول SQL اختباري لجدول typed غير مقسم **B1 فقط**. التطبيق وبياناته لم يتغيرا. الهوية والـrate-limit نقلان اصطناعيان، وactivity في الجدول الأصلي؛ المحول يحقق محاولة typed ثم fallback إلى records عند lookup لكنه لا يدمج جميع المحاولات القديمة مع userRows تلقائيًا. اختبار هذا النموذج لا يثبت تنفيذًا إنتاجيًا أو B2/B3/B4.

**VERIFIED ضمن النموذج:** بداية متزامنة للجهازين بمعرف واحد؛ عدم كشف الإجابة الصحيحة؛ حفظ patchين واستئنافهما؛ رفض وصول مستخدم آخر 409/404؛ تسليم متكرر بنتيجة واحدة وسجل activity واحد؛ save بعد done يرفض؛ حفظ يتزامن مع submit لا يعيد done إلى active؛ deadline v2 لا يقبل إجابات متأخرة؛ محاولة legacy دون timingVersion تحتفظ بهامشها التاريخي؛ اشتراك منتهي أو مسحوب يرد 403 ويخفي المحاولة؛ مالك ينشئ المحتوى ويمنح/يسحب الاشتراك.

هذه حالات محدودة ببيانات اصطناعية وليست اختبارات كل احتمالات التزامن أو جميع حماية F00.6، ولا إثباتًا لعدم إحياء الحساب المحذوف في المحول. اختبارات F00 السابقة لطبقة الهوية وتومبستون لا تُرقى لاختبارات جديدة لـB2/B3/B4.

## Legacy وAtomicity

[tests/ssi-legacy-p02.mjs](../tests/ssi-legacy-p02.mjs) و[نتائجه](evidence/P0.2-SSI-LEGACY.json): سبع محاولات اصطناعية تشمل active/done ونتيجة قديمة وsnapshot وإجابة محفوظة وانتهاء غير مسوى ومحاولتين active للطالب/الامتحان نفسه وحسابًا له tombstone واشتراكًا مسحوبًا، مع activity قديمة.

- **VERIFIED ضمن SQL التجريبي:** تطابق العدد والمعرفات وبيانات JSON وcreated byte-for-byte عند نسخ مجموعة ساكنة؛ إعادة النسخ دون تغيير لم تضف صفوفًا؛ rollback بعد إدراج ثلاثة صفوف من السبعة ترك الهدف فارغًا؛ فشل قيد مؤجل في COMMIT أعاد جميع كتابات معاملة الاختبار؛ activity والتومبستون واشتراك expires=0 لم تتغير. لأن JSON محفوظ كما هو، لم تتغير timestamps/answers/snapshots/نتيجة done في هذه العينة؛ لم يُنفذ تصحيح.
- **FAILED / قرار مطلوب:** إنشاء partial unique index على محاولات active فشل 23505 لوجود صفين legacy. لم يحذف أو يدمج أي صف ولم يُتخذ قرار نيابة عن المالك. لا يصلح اعتماد القيد قبل جرد التكرارات وسياسة صريحة لمعالجتها.
- **FAILED / عائق cutover:** قفل SHARE ROW EXCLUSIVE حجب كتابات اصطناعية تمثل start/save/submit أثناء النسخ، لكن بعد رفعه استمرت الكتابات في الجدول القديم وأصبحت 3 صفوف هدف غير متطابقة. هذه probes SQL وليست ثلاث عمليات handler كاملة. القفل وحده لا يكفي بعد رفعه، و`ON CONFLICT DO NOTHING` لا يزامن تحديثًا لاحقًا.
- قراءة الجدول القديم بعد النسخ بقيت ممكنة، لكن إدراج صف في الجدول الجديد وحده لم يظهر لقارئ الجدول القديم؛ لم يُختبر تشغيل النسخة القديمة كاملة بعد cutover. لم تختبر سلامة COMMIT ذي نتيجة شبكة غير مؤكدة، ولا rollback بعد cutover، أو dual-write/backfill online حقيقي.

التوقف المنضبط للكتابة يتطلب منع كل الكتّاب حتى اكتساب التطابق وتبديل القراءة/الكتابة مع إمكانية رجوع، وليس مجرد قفل ينتهي قبل cutover. Dual-write يحتاج معاملة واحدة للجدولين، barriers للحذف والاشتراك، إعادة المحاولة وidempotency، نقطة تحقق وتوافق للقارئ القديم، وخطة معالجة divergence. لم يعتمد أي خيار.

## الأمان والخصوصية والتعافي

[tests/ssi-roles-p02.mjs](../tests/ssi-roles-p02.mjs): في PostgreSQL حقيقية، `anon` و`authenticated` بلا حق قراءة جدول typed خاص، ودور backend اصطناعي محدود بلا BYPASSRLS يستطيع قراءته بسياسة صريحة. الدور الخلفي يقرأ الصفين؛ عزل الطالب A/B مسؤولية تحقق التطبيق وليست row policy في هذه التجربة. اختبار B1 الفعلي أعلاه يختبر رفض الوصول بين المستخدمين، لكن لا JWT/session حقيقي ولا owner MFA أو إعدادات Supabase.

**BLOCKED:** إثبات أن بيانات الحسابات المقبول حذفها لا تعود بعد backfill أو restore عند استخدام نموذج typed؛ تغطية export/delete وwrite barriers وStorage الفعلية والجلسات في التصميم الجديد؛ نسخة احتياطية واستعادة مع سجلات الحذف والاشتراكات والأكواد الأحدث؛ سياسات RLS/GRANT الحقيقية لجميع الأقسام؛ اختبار إعادة التفعيل أو انتهاء اشتراك بالتزامن مع migration. لا سياسة احتفاظ أو حذف جديدة.

## الحمل ونتائج الأتمتة

لا توجد نتيجة HTTP load للبنى الجديدة. لم تُشغّل مستويات 1/5/10/25 على التطبيق الجديد لأن التكامل والترحيل والأمان لم يجتزوا المعايير؛ لا يجوز وصف 40001 component أو أزمنة COMMIT كـHTTP أو إثبات Zero Unexpected Errors. لا رفع retries أو تغيير SERIALIZABLE أو حدود قبول.

الاختبارات المحلية الأربعة نجحت في قاعدة اصطناعية معزولة: المقارنة، legacy، prototype handlers، وأدوار PG. فشل تشغيل legacy أول مرة بسبب assertion نوع bigint في harness (0 مقابل '0')؛ صُحح اختبار النوع وأعيد بنجاح، دون تغيير بيانات أو سياسة. ظهر تحذير pg عن query متزامن على client في نموذج handlers؛ لم يُعتبر فشلًا صامتًا أو إصلاحًا لموثوقية المحول.

Workflow جديدة `.github/workflows/ssi-p02.yml` تشغل التجارب الأربع على PostgreSQL مؤقتة وبدون أسرار. Quality workflow يتعرف على ملفات التجربة فقط بعد checkpoint P0.1، فلا يعيد baseline/browser الثقيلة دون تغييرات runtime؛ ويُبقي فشل بوابة الحمل ظاهرًا بخطوة حمراء مستقلة. أي ملف خارج القائمة يعيد فحوص quality المعتادة. نتائج GitHub Actions تُراجع في PR #19 ولا تدعي أنها نجحت قبل اكتمالها.
