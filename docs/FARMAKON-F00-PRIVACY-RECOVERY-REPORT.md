## التنفيذ

- `/account/delete` و`POST /api/account/delete` غير متاحين افتراضياً؛ Production ترد 404 حتى إذا ضُبط flag بالخطأ. التفعيل يتطلب Preview، flag صريحاً، حاجز العزل المثبت، strict sessions وquota، مشروع Staging المثبت واتصال DB مطابقاً.
- التحقق من صاحب الجلسة على الخادم، رفض المالك، provider-admin app_metadata، ونمط بريد `f004-delete-…@example.test`؛ لا قبول target user ID من الطلب ولا اعتماد user_metadata. إعادة تحقق كلمة المرور عبر عميل مستقل غير دائم ثم signout محلي للجلسة المؤقتة؛ لا تخزين لكلمة المرور أو token.
- تأكيد عبارة صريحة، same-origin CSRF، حد 3/15 دقيقة لكل مستخدم، body محدود، no-store/no-referrer ورسائل عامة.
- إدراج idempotent في transaction؛ طلب الحذف المقبول يحجب identity لكل platform/media/export/reset. سكربت قاعدة الاختبار يضيف write barriers حتى لا يعيد طلب سابق إنشاء البيانات الشخصية، ويستبعد tombstone من helper جلسات Storage.
- عامل `runSyntheticDeletion` مستقل عن واجهات الجمهور، بلا cron أو endpoint إداري جديد. تسلسل دائم: accepted → sessions_revoked → files_removed → data_removed → complete. lease يمنع عاملين؛ الحالات والمحاولات والوقت تكشف التعطل. فشل خطوة لا يعلن الاكتمال؛ إعادة التشغيل تستأنف خطوات idempotent.
- المزود مبرمج لاستخدام Supabase Admin للحظر ثم إبطال sessions عبر helper ضيق، اكتشاف الملفات اليتيمة من Storage ownership، رفض المشاركة، حذفها عبر API والتحقق، حذف بيانات الاختبار ثم Auth. لا مفاتيح service-role في المتصفح أو المستودع. هذا التكامل **غير مختبر حياً**؛ لا سر عامل متاح في الجلسة ولم أفعل نشره.
- `scripts/staging/f004-synthetic-deletion.sql` خارج migrations التلقائية؛ لم يُطبق على Supabase. يتطلب مراجعة schema وصلاحيات helpers وStorage owner_id ثم تشغيله في Staging فقط. لا تمديد لصلاحيات الدور الحالي. لا تعديل production أو تغير behavior الافتراضي للحسابات.
- أمثلة الاستئناف: أوقف أي عامل سابق وتحقق من انتهائه، افحص state/updated/attempts/lease دون عرض البريد، ثم صفّر lease عالقاً للعملية المحددة فقط قبل استئناف العامل؛ لا lease timeout يسرق عملية خارجية ما زالت تعمل. لا تحذف tombstone لاسترجاع الدخول.

## النسخ والاستعادة

التجربة السابقة كانت pg_dump لصف JSON واحد؛ لا تكفي لاستعادة المنصة كاملة. التجربة الجديدة `tests/recovery-dr.mjs` لا تقبل connection URL أو أي مشروع حقيقي: CI container واسم قاعدة اختباري محددان فقط. تنشئ مصدر ووجهة جديدين، جداول Farmakon الفعلية، نماذج هوية اصطناعية، مالكاً وطالبين واشتراكات ومحاولة وملف PDF اصطناعياً.

نسخة dump مع objects وmanifest داخل غلاف AES-256-GCM بمفتاح عشوائي 256-bit في الذاكرة، nonce عشوائي وAAD ثابت. الملفات المؤقتة 0600 والمجلد 0700؛ يُرفض العبث والمفتاح الخطأ. لا أسرار أو hashes كلمات مرور حقيقية أو roles passwords. لا رفع backup أو مفتاح إلى CI artifacts أو Drive. الاستعادة إلى قاعدة جديدة، hashes للجداول وSHA-256 للمرفق، التحقق من مراجع course/user، RLS لعزل A/B، وإعادة تطبيق سجل حذف أحدث من snapshot قبل السماح بالوصول. تنظيف القاعدتين والملفات والمفتاح في finally.

**هذه استعادة PostgreSQL حقيقية، لكن Auth وStorage نماذج fixtures، وليست استعادة Supabase Auth/Storage كاملة.** لا كلمات مرور حقيقية مستعادة، ولا tokens/jwt signing keys/SMTP/OAuth configurations. إعدادات المصادقة وbucket وMIME وRLS وroles تحتاج manifest مراجعة منفصل؛ ملفات Storage الفعلية لا يغطيها dump قاعدة البيانات.

### إجراء نسخ تشغيلي مقترح لم يُنفذ على بيانات فعلية

1. حدد جهة تخزين وملاك الوصول ومدد الاحتفاظ وRPO/RTO المطلوبة أولاً. لا نسخ إنتاج أو وجهة Drive دون إذن مستقل.
2. قارئ DB مخصص بلا login طويل الأجل أو bypassrls افتراضي؛ SELECT على نطاق النسخ المعتمد فقط. إذا كانت RLS تمنع الاكتمال، تفشل النسخة ويُراجع الدور بدلاً من استعمال حساب التطبيق أو منح امتياز شامل. exporter Objects مستقل read-only للـbucket المعتمد، بلا صلاحية حذف؛ مفاتيحه خارج النسخة والـCI logs.
3. لقطة DB متسقة أثناء توقف الكتابة الاختباري أو PostgreSQL snapshot معتمد؛ لا تدّع اتساق DB والملفات أثناء تغيرها. inventory بعدد وحجم وSHA-256 لكل object، مقارنة مع metadata، ورفض النقص/الزيادة والروابط والمسارات الخارجة. حفظ schema/RLS/grants/migrations وإعدادات غير سرية بمراجعة؛ كلمات مرور الأدوار ومفاتيح Auth/SMTP/OAuth خارج الحزمة المشفرة في مخزن أسرار منفصل.
4. نقل الحزمة بتشفير موثق ومفتاح خارج موقع النسخة، checksum للملف المشفر وفك تجريبي؛ فشل أي فحص يمنع وسم النسخة كاملة. لا تمرير مفتاح في command line أو commit أو log. أداة التجربة مفتاحها مؤقت عمداً، فلا تمثل نظام حفظ مفاتيح طويل الأجل.
5. استعادة في مشروع/قاعدة جديدة معزولة، الشبكة وSMTP وwebhooks والمستخدمون ممنوعون افتراضياً؛ إدارة roles بأسرار جديدة، وعدم إعادة tokens/sessions. اختبر Auth وفق مسار Supabase المدعوم قبل السماح بالوصول. استعادة Storage بالـAPI والـchecksum وليس INSERT metadata فقط.
6. طبّق deletion ledger الأحدث من snapshot قبل فتح الخدمة، وأعد اختبارات الهوية والاشتراك والتصدير والعزل والملفات. لا تعتمد restore إذا تعذر الحصول على سجل الحذف الأحدث؛ quarantine تبقى مغلقة.
7. انتهاء مدة النسخة أو حذف المفتاح لا يحددان هنا قبل اعتماد السياسة. النسخة القديمة لا تُعد إثبات محو آني؛ احصر الوصول وأعد تطبيق الحذف عند الاستعادة.

مراجع رسمية تمت مراجعتها: [Backups](https://supabase.com/docs/guides/platform/backups)، [Admin deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser). محاولة جلب changelog.md رفضتها أداة التصفح بسبب content-type؛ لم أنسب إليه مراجعة ناجحة. لا تفعيل Pro/PITR أو خدمة مدفوعة.

## الاختبارات والحالة الحالية

محلياً: typecheck وbuild وbackend/auth/callback/privacy/http/isolation/PWA ناجحة. اختبارات Auth وStorage المحاكية موسومة كذلك. النتائج الجديدة في CI تُضاف بعد انتهاء تشغيل هذا الالتزام؛ لا ننسب نجاح 40381458331 إلى F00.4.

الحذف الحي لحساب Supabase اصطناعي وإثبات login failure بعد الحذف، JWT القديم وStorage الحقيقي: **غير منفذ** لغياب اعتماد عامل Staging وسرّه الآمن؛ لا أستبدله بنجاح الـfixtures. لا إنشاء أو حذف حسابات Supabase في هذه الجولة. اختبار نفس البريد محلياً يمنع إحياء الحقوق بواسطة tombstone؛ سياسة إعادة التسجيل الحقيقية معلقة.

لا نشر Preview جديدة؛ النشر التلقائي للفرع ما زال مغلقاً. لم أخفض Deployment Protection أو أغير Vercel/Supabase environments. معلومات Preview السابقة تخص تقرير F00.3، وليست إعادة فحص حية لجميع إعداداتها في هذه الجولة. لا claims بأن F00.4 منشورة.

## التراجع والمخاطر وبوابات F00

- flag يبقى معطلاً؛ revert لكود F00.4 لا يغيّر بيانات لأن SQL غير مطبق. بعد تطبيقه مستقبلاً: لا تعطل tombstone/session barriers أثناء وجود طلب حذف؛ أوقف القبول والعامل وأبقِ الحجب حتى المراجعة. حذف Auth/Objects نهائي لا يعكسه revert للكود. لا تعد الحساب من نسخة قديمة تلقائياً.
- signed Storage URLs السابقة قد تبقى حتى TTL (60 ثانية في الخادم)، والملفات المحلية المستقلة لا تسترجع. منع الوصول عبر التطبيق لا يعد DRM أو محواً عن بعد.
- المفاتيح الخدمية لـSupabase واسعة الصلاحيات بطبيعتها؛ لم تُنشأ أو تُمنح للتطبيق هنا. يلزم عامل معزول وأسرار قصيرة العمر وحصر نطاقه وقرارات retention قبل تجربة حية؛ helpers SQL لا تمنح قراءة مباشرة لـAuth.
- يدعم المسار البيانات الحالية المعروفة؛ أي نوع ملكية جديد أو ملفات مشتركة يوقف التنفيذ للمراجعة. لا توجد ميزة Flashcards جديدة هنا.
- بوابات مفتوحة: بريد F00.3 والتأكيد والاستعادة ورفض الروابط المستهلكة/المنتهية؛ JWT الطبيعي وتجديده؛ إعدادات Auth المباشرة؛ حذف حي مع Storage/Auth؛ سياسة احتفاظ قانونية/مالية معتمدة؛ Auth/Storage DR كامل؛ backup destination/key custody/retention/RPO/RTO معتمدة؛ اختبارات الأداء والوصولية وتوقيت الامتحان الباقية في F00.
