## 6. Next مقابل Supabase بعد قبول الطلب وبعد الحذف

| المسار/المحاولة | Next بعد Accepted | Next بعد Complete |
| --- | --- | --- |
| GET platform، بما يعرض الملاحظات والمحاولات | 401 | 401 |
| POST platform وكتابة التقدم/الملاحظات | 401 | 401 |
| بدء/حفظ/تسليم الامتحان | 401 | 401 |
| GET media / تحميل الملف المحمي | 401 | 401 |
| Export study data | 401 | 401 |
| تغيير كلمة المرور بالجلسة الملغاة | 401 | 401 |
| cookies الأصلية والجهاز الثاني | 401 | 401 |
| تكرار طلب الحذف | 401 | 401 |
| تسجيل الدخول بكلمة صحيحة سابقاً | لم يُستخدم لإثبات JWT expiry | 400 عام من Next بعد حذف Auth |

قبل الحذف كان A قادراً فعلياً على قراءة ملفه وبدء امتحان وحفظ المحاولة، وكانت ملاحظات A وB مأهولة. بعد الحجب لم يُكتفَ بإخفاء الواجهة؛ رفضت handlers هذه الطلبات قبل قراءة المحتوى أو تغييره.

Supabase المباشر اختُبر بصورة مستقلة: Storage بطلب جديد وJWT سابق=400، وAuth update بالتوكن السابق بعد الحذف=403. ليست هذه أكواد Next ولا يُخلط بينهما. جدول deletion_jobs غير قابل للقراءة للمستخدم العادي: PostgREST private profile=406، وRLS=true، ولا SELECT grants إلى anon/authenticated بحسب فحص SQL.

## 7. العامل ومراحل الفشل والاستئناف

استُعمل `runSyntheticDeletion` الموجود، مع كود coordinator/store/provider نفسه داخل حزمة Edge ونقل SQL مناسب لـDeno. لم يُضف Cron أو عامل دائم. لا يُقبل أي target user ID أو SQL من طلب العامل؛ يعمل على هوية A ذات الاسم والوسم الإداري الثابتين لهذه الجولة فقط.

1. Accepted أُنشئت من **واجهة Next**، وليست إدراجاً إدارياً بديلاً لقبول المستخدم.
2. العامل حظر دخول A وأبطل جلساته، ثم توقف عند مرجع ملف مشترك: sessions_revoked، والملفان باقيان.
3. عولج مرجع المشاركة **الاصطناعي فقط**، دون حذف بيانات B أو ملفه.
4. fault Storage محقون عند الحد: بقيت sessions_revoked وقابلية الاستئناف.
5. التشغيل التالي حذف ملف A، ثم fault DB عند purge: files_removed.
6. التشغيل التالي حذف بيانات A، ثم fault Auth قبل deleteUser: data_removed.
7. الاستئناف الأخير حذف Auth ووصل إلى Complete. إعادة التشغيل لا تعيد خطوة مدمرة؛ lease فارغ. **5 محاولات عامل** إجمالاً.

الفشل المحقون اختبار حدود adapter، وليس ادعاء إحداث outage فعلي لـSupabase أو PostgreSQL. العمليات المحيطة به استعملت الخدمات الحقيقية. اختبار Snapshot/deletion-ledger القديم في CI بقي ناجحاً؛ لم ننشئ نسخة من بيانات الإنتاج.

## 8. حدود الروابط الموقعة والملفات المحلية

اختبار منفصل على B: أُصدر رابط صالح 60 ثانية، ثم أُلغيت جلسته المحلية فعلياً. Next=401 وطلب Storage جديد=400، **لكن الرابط الموقع السابق أعاد 200 داخل TTL**. بعد انقضاء المهلة أعاد 400 دون حذف ملف B، ثم نجح دخول B مجدداً وقراءة الملف نفسه. هذا يثبت استقلال عمر المنحة الموقعة عن الجلسة، ولا يُعرض على أنه عيب أُزيل بالحذف.

نسخ PDF المستلمة والكاش المستقل لا تُمحى عن بعد. cacheControl=0 للرفعات الجديدة لا يمحو كاشاً سابقاً. لا اختبار DRM أو ضمان إلغاء آني لكل رابط قديم. [أدلة الرابط الآمنة](evidence/F00.5-SIGNED-GRANT-RESULTS.json) لا تتضمن الرابط نفسه.

## 10. نتائج CI والأدلة

[نتائج التطبيق الحية](evidence/F00.5-LIVE-RESULTS.json) مثبتة على `dca1525` وDeployment الاختبار المذكور. اختبارات CI للنقل الوهمي موسومة منفصلة؛ لا تُنسب إليها نتائج Auth الحي. فحوص TypeScript/build/privacy محلياً ناجحة. تعاد baseline/postgres/browser على رأس التسليم الذي يضم الأدلة والاختبارات؛ رابط النتيجة الدقيقة في وصف PR. إذا فشل رأس جديد فلا يُحسب نجاح الرأس القديم بديلاً.

يشمل postgres الاختبارات القائمة للـRLS/concurrency/export/deletion وbackup/restore الاصطناعي المشفر. تبقى استعادة Auth/Storage الكاملة خارج الإثبات، ولا يُعاد وصف PASS_PARTIAL بأنها استعادة إنتاجية.

## 11. خطة التراجع

لا migration جديدة تُعكس في F00.5. التراجع عن تعديل UI/API على فرع مراجعة لا يعيد حساباً محذوفاً. أبقِ tombstones وstrict-session helpers وحاجز العزل، ولا تحذف overrides فتعود Preview لوراثة DB الإنتاج. أوقف قبول طلبات جديدة وأغلق العامل قبل تغيير نشر المراجعة، وأعد المالك وflag=false كما فُعل هنا. لا تستعد مستخدماً محذوفاً من Snapshot قديم دون replay لسجل الحذف وسياسة معتمدة. لا merge أو rollback إنتاجي.

| بوابة الحذف وNext Preview الحية لهذه الجولة | Passed ضمن النطاق | الأدلة أعلاه؛ لا تعني إتاحة عامة أو إغلاق سياسة الاحتفاظ |
| Critical/High مفتوحة مكتشفة في هذه الجولة | لا جديدة مثبتة | حدود signed grants والكاش موثقة، والبوابات الأوسع باقية؛ لا ادعاء خلو مطلق من الثغرات |

## 13. قرارات المالك

مراجعة واعتماد سياسة الاحتفاظ والحذف وإعادة التسجيل، وتحديد آلية عامل دائم وصلاحيات تشغيله قبل إتاحة حقيقية. توفير مسار بريد اختباري ووصول مراجعة إعدادات Auth، واعتماد نطاق DR الكامل وأهداف RPO/RTO. قرار اتصال Staging قبل انتهاء الدور إذا استمر العمل بعد 2 نوفمبر؛ لا تمديد تلقائي. لا موافقة نشر Production مفهومة من نجاح هذه الجولة.

## 14. الحكم

**Passed** للنشر المحمي المعزول، وواجهة الحذف والجلسات وNext/Storage الحقيقية ضمن السيناريوهات المحددة، والاستئناف والتنظيف. **Blocked** للبوابات المسجلة أعلاه. لا فشل وظيفي غير معالج مثبت في F00.5، ولا جاهزية إنتاجية شاملة. Issue #1 وDraft PR يبقيان مفتوحين، والتوقف هنا عند F00.5 دون F01/F11/F12 أو دمج أو Production.
