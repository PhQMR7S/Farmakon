# Farmakon P0.3 — تقرير أمان نموذج نقل الامتحانات

التاريخ: 28 أكتوبر 2026. البداية من `f9f8d1c848fc1a95c07cfe9d7e541596c72aae58`، [Draft PR #19](https://github.com/PhQMR7S/Farmakon/pull/19) المبني على فرع التدقيق ويعتمد على #18 و#17. لا تعديل runtime أو migration فعلية أو أسعار/اشتراكات أو سياسة F00.6.

## الحكم

**PARTIAL / EXPERIMENT — غير جاهز للترحيل أو cutover، وبوابة SSI ما زالت FAILED / OPEN.** نموذج SQL للتوقف والكتابة المزدوجة يعمل ضمن fixtures محددة، لكن كاتبًا قديمًا لا يلتزم بالقفل يستطيع تجاوزه، ولا يوجد تكامل حقيقي يثبت إلزام جميع الكتّاب، وعمليات حذف/export ومزود Supabase والعودة من cutover لم تثبت. لا يوجد إصلاح runtime أو نجاح حمل جديد. التشغيل السابق فشل عند 10 VU بـ503 / 40001، ولم ينفذ 25 VU.

## 1. التكرارات والبيانات القديمة

[tests/ssi-migration-p03.mjs](../tests/ssi-migration-p03.mjs) ينشئ سبع محاولات اصطناعية منها active مكررتان لنفس الطالب والامتحان، done بنتيجة وsnapshot، منتهية، وحساب عليه tombstone واشتراك مسحوب. استعلام read-only وجد مجموعة التكرار وأبقى المحاولتين وإجاباتهما. نموذج **حجز على مستوى مجموعة الطالب/الامتحان** يمنع إنشاء حجز جديد لنفس المجموعة دون اختيار أحد السجلين فائزًا أو تعديل وضعهما. هذا اختبار قيد الحجز فقط؛ لا يضمن أن handlers القديمة أو كاتبًا لا يشارك في البروتوكول سيحترمه. تحديد سلوك عرض المحاولتين عند الاستئناف وتسويتهما يتطلب قرار المالك؛ لا حذف ولا إعادة تصحيح تلقائي.

تحققت fixtures من تطابق IDs وJSON عند النسخ، وبقاء سجل done ودرجة وإجابات، والتكرارين والاشتراك المسحوب في المصدر. لا يوجد إثبات شامل لكل أقدم بيانات الإنتاج أو ملكية نتائج قديمة في مزود حقيقي.

## 2. نموذج A — Write Fence

داخل PostgreSQL 17 معزول، أخذ كاتب اصطناعي قفل مشاركة على صف تحكم؛ معاملة cutover انتظرت حتى انتهى. نسخت المحاولات وبدلت marker في المعاملة نفسها، ثم طابقت IDs وJSON؛ فشل قبل COMMIT تراجع فيه الهدف والـmarker. أثناء الانتظار وقع SQLSTATE 40001 فعلي، أعيدت معاملة cutover كاملة مرة ونجحت. كاتب **ملتزم** قرأ marker وكتب الجديد بعد cutover.

**FAILED كحل متكامل:** نفذ كاتب قديم لا يقرأ marker كتابة في records بعد cutover وأحدث divergence. البروتوكول لا يحجز كل كاتب start/save/submit/settlement/delete، ولا يمنع SQL خارجيًا. لا تصلح نتيجة النموذج كضمان لإيقاف جميع الكتابات أو انتقال حقيقي. لم تختبر نسخة قديمة كاملة بعد cutover، أو استعادة حقول جديدة منها.

## 3. نموذج B — Transactional Dual-Write

في اختبار SQL واحد، تحديث المصدر والهدف وevent وسجل operation-ID تقع في معاملة SERIALIZABLE واحدة. تحقق الاختبار من:
- فشل اصطناعي بعد كتابة المصدر، أو غياب صف الظل، يعيدان المصدر ويمنعان تسجيل العملية.
- save وsubmit وsettlement ونتيجة محفوظة، event واحد، وعدم تعديل نتيجة done عند submit لاحق.
- tombstone اصطناعي يرفض كتابة الحساب المحذوف؛ حذف اصطناعي من النسختين في معاملة.
- 40001 يُثار من PostgreSQL بعد كتابة المصدر؛ ROLLBACK يمنع كتابة جزئية.
- تكرار operation-ID مع طلب مختلف يرفض. محاكاة فقد **رد بعد COMMIT ناجح** تستخدم operation-ID ثابت وhash تجريبي وتستعلم عن السجل قبل الإجابة بأنه سبق التنفيذ.

**حدود مهمة:** هذه محاكاة فقد رد، لا قطع شبكة حقيقي أو إثبات outcome مجهول لـCOMMIT. hash النموذج يغطي معرف/نوع العملية فقط وليس هوية العميل والحمولة الكاملة أو ربط الصلاحية. جدول operation-ID وevent اختباريان، لا توجد سياسة إدارة أو retention معتمدة. لا تكرار أعمى لـCOMMIT غير المتيقن؛ يلزم معرف ثابت موثق وقراءة حالة موثوقة قبل أي قرار، مع حالات غياب النتيجة/انقطاع القراءة. لم تختبر منافسة حقيقية بين delete وbackfill عبر جميع الكتّاب أو atomicity مزود Auth/Storage.

## 4. تحذير pg ومسارات التطبيق

إعادة تشغيل تشخيص P0.2 مع `--trace-deprecation` حددت المصدر: `GET /api/platform` ينفذ `Promise.all` لقراءات الكتالوج داخل transaction واحدة، و`lib/database.ts` يربطها بعميل PG واحد؛ التحذير يظهر في `publishedRows → Statement.all → Client.query`. هذا سلوك في مسار التطبيق المستخدم في harness، وليس مجرد رسالة يمكن حذفها من الاختبار.

[tests/ssi-runtime-p03.mjs](../tests/ssi-runtime-p03.mjs) يعدّل **المحول الاختباري وحده** لتسلسل استعلامات كل transaction، ويكتب المحاولات إلى typed غير مقسم والمصدر في المعاملة نفسها. اختفى التحذير في هذا الاختبار، وبقي runtime الفعلي دون تعديل. ثبت ضمن test transport: جهازان يبدأان محاولة واحدة؛ حفظ patchين؛ استئناف؛ حجب answer key؛ عزل A/B؛ submit مكرر؛ save بعد done؛ حفظ/submit متزامنان؛ v2 deadline؛ legacy grace؛ اشتراك منتهي/مسحوب؛ event واحد وتطابق بيانات النسختين في الحالات التي نفذت.

**BLOCKED:** النموذج ليس تنفيذ write-fence أو بروتوكول operation-ID أعلاه داخل handlers، ولا يغطي جميع بيانات legacy (userRows لا تدمج القديم غير المنقول)، ولا B2/B3/B4، ولا tombstone حقيقي أو جميع حالات انتهاء/حذف متزامنة. الـAuth/session/rate transport اصطناعية؛ لا تكامل Supabase حي. تسلسل المحول الاختباري لا يصلح runtime أو يثبت توافق إصدار pg مستقبلي.

## 5. RLS والخصوصية والنسخ والاستعادة

[tests/ssi-privacy-p03.mjs](../tests/ssi-privacy-p03.mjs): أدوار PG اصطناعية A/B/owner/backend/visitor، RLS يحد الطالب إلى صفه ويتيح owner/backend، والزائر مرفوض؛ snapshot داخل قاعدة وreconciliation اصطناعي يستبعد صف حساب محذوف ويحافظ على اشتراك سُحب بعد snapshot. هذا نموذج أدوار لا JWT أو Storage Supabase حقيقي. لم تختبر سياسات المزود أو الحسابات المحذوفة فعليًا، ولم تختبر endpoint export/delete الفعليين على البنية الجديدة.

[tests/ssi-backup-p03.mjs](../tests/ssi-backup-p03.mjs): `pg_dump` وrestore إلى قاعدة منفصلة اصطناعية داخل حاوية PostgreSQL، ومطابقة checksum للصفوف، ثم تطبيق tombstone وسحب صلاحية أحدث اصطناعيًا قبل فتح البيانات. تم حذف قاعدة الاستعادة والـschema الاختباريتين. لا استعادة Auth/Storage أو إثبات freshness لمصدر ledger مستقل، ولا ضمان أمان restore الحقيقي عند فقد دفتر الحذف أو الاشتراكات. RLS/schema/roles والجلسات ومفاتيح التخزين وعمليات النسخ الفعلية تحتاج اختبارًا وتصميمًا مستقلين.

## 6. الأداء والقرار

لم تكرر P0.2 دون فرضية جديدة. المقارنة السابقة A/B1/B2/B3/B4 أعطت 40/39/13/9/1 حالات 40001 من 80 زوجًا على PostgreSQL بعميلين و1200 صف طالب؛ ليست نتيجة HTTP أو سعة. لم نختبر كلفة fence/dual-write على الأحمال، أحجام الفهارس، نقل/restoration مقابل الأقسام، أو 1/5/10/25 VU لأن التوافق الوظيفي والهجرة والأمان لم يجتزوا المعايير. لا اختيار تلقائي لـ32 قسمًا، ولا زيادة retries أو تغيير SERIALIZABLE أو Zero Unexpected Errors.

## 8. التراجع وقرارات المالك

التراجع الحالي: revert ملفات اختبارات/workflow/report/evidence فقط؛ لا تغيير بيانات أو مخطط في أي خدمة. قبل أي cutover لاحق يلزم حصر التكرارات دون تغييرها، قرار تجربة الطالب/التسوية، بروتوكول إيقاف جميع الكتّاب أو dual-write متوافق مع النسخة القديمة، خريطة كاملة للحذف والـtombstones والاستحقاقات وexport، مصدر ledger موثوق وحدوده، إثبات rollback آمن عند كتابة جديدة وCOMMIT غير مؤكدة، اختبار Auth/Storage وrestore فعليين، ومراجعة أدوار RLS والاختبار المتزامن، ثم اختيار أقسام وقياس تكلفة وحمل ضمن الحدود. لا policy أو حذف أو retention اختير بالنيابة عن المالك.

**هل البنية جاهزة لاختبار تطبيق فعلي لاحق؟** لا بعد: يلزم أولًا تصميم واحد متكامل يغلق تجاوز الكتّاب القدامى وفجوات الهوية والبيانات القديمة وrollback. يمكن مراجعة النماذج الاختبارية كأدلة هندسية، لا كخطة نشر.

لا Production أو Staging أو بيانات حقيقية أو Google Drive، لا خدمات مدفوعة أو دمج/نشر، ولا تنزيل صور Supabase المحظورة.
