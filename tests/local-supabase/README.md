# F00.10 isolated Supabase validation

Opt-in only. `local-supabase.yml` accepts `workflow_dispatch` on the audit branch,
or adding the exact `run-f0010-local` label to same-repository Draft PR #18.
The label path is needed while the workflow is absent from the default branch.
Remove and re-add the label only for an intentional rerun. Never merge merely to
enable manual dispatch. Normal pushes and PR synchronizations do not run it.

Two serial matrix jobs each receive a fresh standard public GitHub-hosted Ubuntu
24.04 runner. The preflight requires a public repository, working Docker,
7 GiB available RAM and 10 GiB free disk. Each job is limited to 25 minutes.
No larger runner, paid service, artifact upload, cache, cloud login or Supabase
project linking is configured. Node 24 and Supabase CLI **2.81.3** are pinned;
the CLI version's config template and help were reviewed. CLI container image
versions are selected by that release and printed without credentials.
The official `ghcr.io/supabase` mirror is selected using the pinned CLI's
supported registry setting, also used by its own CI. No registry credentials
are supplied. The initial ECR attempts failed with `Data limit exceeded`;
these failures remain part of the report. Startup is bounded to eight minutes.

The stack is created under RUNNER_TEMP, on a separate network whose published
ports default to 127.0.0.1. The test audits every binding before using services.
Status/start/application logs stay in a private 0700 directory with umask 077;
they may contain synthetic credentials and MUST NOT be uploaded or printed.
Only fixed check names, HTTP status numbers, resource counts and image names
may enter Actions logs. HTTP helpers accept exact loopback origins; no hosted
project URLs or credentials are accepted as inputs. No real mailbox is used.

SQL is an explicit reviewed allowlist: baseline bootstrap, private quota,
Storage ACL and strict session helper. Files historically named Staging-only
are used here solely against a newly created disposable local DB after URL
checks. No glob of repo migrations is applied. F00.7 index, temporary Staging
role and synthetic deletion worker SQL are excluded. No Production behavior
or Staging settings change. All content is generated by this test.

The actual built Next application runs only on 127.0.0.1:3000 for signup,
PKCE callback and reset. DB SSL is disabled **only in this disposable loopback
test connection string**; application TLS checks are unchanged. Auth and
Storage requests use real local services, not transport mocks. File reads use
the genuine Farmakon course entitlement/owner/session policies, not an invented
per-user Storage policy. Uploads are by a synthetic owner; A/B are read-only
students enrolled in separate synthetic courses. A third signup is used to test
an external `next` with a valid PKCE grant; the owner is created by local Admin API.

Natural JWT expiry is short (90 seconds) in this local config only. No forged
JWT or changed clock. Mailpit delivery does not prove Staging SMTP, and local
configuration does not prove Staging configuration. This task creates/tests a
clean environment; it does **not** copy or restore Auth, Storage or a backup.

`run.sh` traps cleanup and the workflow has an always-cleanup audit. Exact local
project containers and volumes must be absent, the private directory removed,
and the dedicated network removed. A runner killed by the platform may skip
the trap: its fresh ephemeral VM is then the final disposal boundary; do not
claim an observed cleanup success if its step did not finish.

Reproduce by the opt-in workflow on a fresh authorized runner. Local scripts
refuse a non-Actions/non-repository context to avoid accidentally targeting
the user's workstation. No database dumps, snapshots, keys or mail bodies are
saved to git/Drive/Actions artifacts.
